# PR レビュー

このPRをレビューしてください。**コードと設計ドキュメントの双方** に対応するモード型ワークフローです。

---

## 引数

| 引数 | 動作 |
|------|------|
| `/review` | **自動判定モード**(変更ファイルから code / design を判定) |
| `/review code` | コードレビューモード(明示) |
| `/review design` | 設計ドキュメントレビューモード(明示) |
| `/review --since=<comment-id>` | 指定コメント ID 以降の差分のみ再レビュー(指摘の解決状況を中心に確認) |
| `/review <自由記述>` | 視点・ファイル指定など(例: `/review design セキュリティ視点だけ`) |

複数引数の併用可。例: `/review design --since=4365084235`

---

## 用語(汎用語彙)

本ルールは特定のワークフロー固有名詞に依存しないよう、以下の **抽象語彙** を使用する。AIDLC ワークフローの具体ファイルへのマッピングは末尾の「AIDLC マッピング」セクション参照。

| 抽象語彙 | 定義 |
|---------|------|
| **上流文書** | 本 PR の成果物が依拠する上位の確定済み文書(要件 / ペルソナ / ストーリー等) |
| **下流文書 / 後続ステージ** | 本 PR の成果物を前提に、後で詳細化される文書やステージ |
| **マスター文書** | ある責務・要素を **最初に定義** している文書(単一情報源) |
| **派生文書** | マスター文書の内容を引用 / 図示 / 要約している文書(例: シーケンス図、依存マトリクス) |

---

## 前提

- AI 支援開発(Claude Code 等)で生成・修正された成果物が含まれる前提でレビューする
- 各視点から独立して評価し、重複する指摘も視点ごとに明記する
- 参考基準: [Google Engineering Practices](https://google.github.io/eng-practices/review/)

---

## 手順

1. `gh pr view --json body` で PR 説明文を取得し、**事前確認**を実施
2. 事前確認で Critical があれば、その時点で報告してレビューを中断
3. **モード自動判定**(引数で明示されていない場合)
4. **PR 規模・形態の判定** を実施(空 PR / リバート / 巨大 PR への分岐)
5. `git diff main...HEAD` で変更差分を確認
6. **カバレッジ宣言** を出力先頭に提示(読んだ / 読んでいないファイルとその理由)
7. **モード別の視点** で順番にレビューを実施(各指摘に **信頼度 / 根拠視点・根拠項目** を必須付与)
8. **重要度判定基準マトリクス** に従ってラベリング
9. 総合評価を出力(`Critical / ❓ Speculative` はマージブロックではなく要検証扱い)
10. 出力末尾に **メタフィードバック節** を必須記載(空でも明示)
11. **再レビュー(`--since`)モード** の場合は手順 7 を「前回指摘の解決状況確認 + 新規検出の `🆕 New / 🙇 Missed / 🔄 Resurfaced` 分類」に置換

---

## モード自動判定アルゴリズム

`git diff main...HEAD --name-only` で変更ファイル一覧を取得し、以下の優先順位で判定:

1. 以下のいずれかに該当するファイルがあれば **code 属性あり**
   - 実装言語ファイル: `.rs` / `.ts` / `.tsx` / `.js` / `.jsx` / `.py` / `.go` / `.java` / `.rb` / `.kt` / `.swift` / `.cs` / `.cpp` / `.c` / `.h` / `.scala` / `.php`
   - 依存マニフェスト: `package.json` / `Cargo.toml` / `go.mod` / `pyproject.toml` / `Gemfile` / `pom.xml` / `requirements.txt`
   - ロックファイル: `package-lock.json` / `Cargo.lock` / `poetry.lock` / `Gemfile.lock` / `yarn.lock` / `pnpm-lock.yaml`
   - CI / リポジトリ設定: `.github/workflows/` / `.github/`
   - インフラ定義: `*.tf` / `*.yaml`(k8s 等) / `Dockerfile` / `wrangler.toml` / `compose.yaml` / `Containerfile`
   - DB / 運用スクリプト: `*.sql`(マイグレーション) / `*.sh` / `*.bash` / `Makefile`
2. 変更が `*.md` のみ、または `docs/` / 設計文書ディレクトリ(本リポジトリでは `aidlc-docs/` 配下)のみであれば **design 属性あり**
3. 判定結果:
   - **code 属性のみ** → **code モード**(code 5 視点)
   - **design 属性のみ** → **design モード**(design 5 視点)
   - **両方(ハイブリッド PR)** → **ハイブリッドモード**: **code 5 視点 + design 5 視点 = 全 10 視点を独立に実施**。視点間で観点が重複する場合も統合せず、相互検証として両方記載する

判定結果は最初に明示する(例: 「自動判定: ハイブリッドモード — 実装ファイル + 設計文書の両方を含む、全 10 視点を独立実施」)。

## PR 規模・形態の判定

レビュー実行前に、PR の **規模(変更行数)** と **形態(コミット種別)** を判定し、必要に応じて分岐する。これらは言語・フレームワーク・ワークフローを問わず適用される普遍的なエッジケースである。

### 規模軸

`git diff main...HEAD --shortstat` で総変更行数(追加 + 削除)を取得し、以下に従う:

| 規模 | 行数 | 動作 |
|------|------|------|
| 小 | < 200 | 標準レビュー |
| 中 | 200〜1,000 | 標準レビュー |
| 大 | 1,000〜5,000 | 標準レビュー + 「集中視点」を冒頭で宣言(視点間で時間配分を傾斜)、関連性の弱いファイルは抜粋確認可 |
| 超大 | > 5,000 | **冒頭で 🟡 Warning「PR 分割推奨」を提示** した上でレビュー実施(分割せず審査を強行する場合の見落としリスクを著者に明示) |

判定行数はカバレッジ宣言にも記載する。

### 形態軸

`git log main..HEAD --format=%s` でコミット件数・件名・親数を取得し、以下に従う:

| 形態 | 検出条件 | 動作 |
|------|---------|------|
| **マージコミットのみ PR** | 全コミットがマージコミット(`git log --merges` のみ) | レビューせず「no reviewable change(マージコミットのみ)」を出力して早期終了 |
| **リバート PR** | コミットメッセージが `Revert "..."` または `revert:` で始まる | 「リバート対象コミット」と本 PR の差分を別途確認(手動でリバート差分を再導入していないか) |
| **ドラフト PR** | `gh pr view --json isDraft` が true | 事前確認の必須項目を **推奨** に緩和、視点レビューは標準実施 |
| **空 PR** | 変更ファイル 0 件 | レビュー対象なし、Note のみ返答 |

該当形態がある場合、判定結果と発動した分岐内容をカバレッジ宣言に記載する。

## 事前確認: 📋 PR テンプレート準拠

**目的**: PR の説明がプロジェクトのテンプレート(`.github/pull_request_template.md`)に従って記入されているか確認する。

**判定基準**: 未記入・コメントのみ・デフォルト値のままの項目は重要度判定基準マトリクス(後述)に従って判定。

### PR 属性ごとの確認項目(属性 OR 集合)

PR テンプレート冒頭の **「PR 属性」** セクションでチェックされた属性すべてに対して、各属性の確認基準を OR で適用する(複数属性チェックされている場合、いずれか厳しい方を採用)。属性未指定の場合はデフォルトで **changes-code** とみなす。

| 確認項目 | changes-code | changes-docs | changes-infra | changes-config | changes-aidlc-stage |
|---------|:-:|:-:|:-:|:-:|:-:|
| **概要**(目的・背景) | 🔴 必須 | 🔴 必須 | 🔴 必須 | 🔴 必須 | 🔴 必須 |
| **変更内容**(箇条書き) | 🔴 必須 | 🔴 必須 | 🔴 必須 | 🔴 必須 | 🔴 必須 |
| **関連 Issue / PR / コメント** | 🟡 推奨 | 🟡 推奨 | 🟡 推奨 | 🟡 推奨 | 🟡 推奨 |
| **動作確認**(ローカル動作・既存影響) | 🔴 必須 | N/A | 🔴 必須 | 🔴 必須(CI 結果も可) | 緩和(下記必須欄で代替) |
| **上流成果物との整合性確認** | N/A | N/A | N/A | N/A | 🔴 必須 |
| **レビュー観点** | 🟡 推奨 | 🟡 推奨 | 🟡 推奨 | 🟡 推奨 | 🟡 推奨 |

Critical が 1 件でもある場合、コードレビューを中断し PR 説明の修正を促す。事前確認は **すべての PR に一律適用** する(過去 PR への遡及適用の経過措置は設けない — テンプレートが導入されている時点で全 PR が判定対象となる)。

## code モード: 5 視点

### 👔 視点 1: プロダクトオーナー視点

**目的**: 変更がビジネス価値・要件と整合しているか確認する。

**確認項目**:
- [ ] PR の説明が変更の目的・背景を明確に説明しているか
- [ ] 実装が Issue / 要件の意図を正確に実現しているか(AI がビジネス意図を誤解していないか)
- [ ] スコープクリープ(要求外の変更・機能追加)がないか
- [ ] ユーザーへの影響(動作・UX 変化)が明確か
- [ ] 変更に伴うドキュメント・README の更新が必要か
- [ ] **段階間整合性**(上流文書を持つ PR の場合): 本 PR で確定した判断により上流文書への **逆波及更新** が必要か
- [ ] **構築可能性**(設計変更を伴う場合): 後続実装段階で詰まりそうな未確定事項に「TBD / 解決時期 / 解決責任者」が明示されているか
- [ ] 将来の要件変更に対して過度に依存した設計になっていないか

### 🧪 視点 2: 品質保証 (QA) 視点

**目的**: テスト品質・ロジック正確性・リグレッションリスクを確認する。

**確認項目**:
- [ ] 変更に対応するテスト(ユニット/統合)が追加・更新されているか
- [ ] エッジケース(境界値・null・空配列・タイムアウト等)がカバーされているか
- [ ] AI が生成したロジックに「それらしいが間違った」実装がないか(ハルシネーション検出)
- [ ] 既存テストへの影響(壊れるテストがないか)を確認したか
- [ ] 異常系・エラーパスのテストが存在するか
- [ ] 手動テストが必要な箇所が明示されているか
- [ ] CI/CD が正常に通る見込みがあるか

### 💻 視点 3: 開発者視点

**目的**: コード品質・設計・保守性を確認する(Google Engineering Practices 準拠)。

**確認項目**:
- [ ] **設計**: アーキテクチャ・モジュール構成が適切か(過剰な抽象化・AI による不要コードがないか)
- [ ] **複雑性**: 関数・クラスが単一責任を持ち、レビュアーが理解できる複雑さか
- [ ] **命名**: 変数・関数・クラス名が意図を明確に表しているか
- [ ] **コメント**: 「何を」でなく「なぜ」を説明するコメントが書かれているか
- [ ] **DRY**: コードの重複がないか
- [ ] **エラーハンドリング**: 外部 API・DB への呼び出しに適切な例外処理があるか
- [ ] **パフォーマンス**: N+1 問題・不要なループ・過剰な API 呼び出しがないか
- [ ] **コミットメッセージ**: プロジェクト規約(`<type>: <日本語メッセージ>`形式)に従っているか

### 🔒 視点 4: セキュリティ視点

**目的**: AI 生成コード特有のセキュリティリスクを含む脆弱性を確認する。

参考: [Vibe Coding Security - Checkmarx](https://checkmarx.com/blog/security-in-vibe-coding/) / [AI-Generated Code Vulnerabilities - Vidoc Security Lab](https://blog.vidocsecurity.com/blog/vibe-coding-security-vulnerabilities)

**確認項目**:
- [ ] **シークレット**: API キー・パスワード・トークンがコード・設定ファイルにハードコードされていないか
- [ ] **認証**: 認証ロジックが AI の「それらしい実装」でなく、正しく機能するか
- [ ] **認可 (BOLA)**: リソース ID で参照する処理で、呼び出し元の所有権確認があるか
- [ ] **インジェクション**: SQL クエリ・OS コマンド・テンプレートに文字列結合を使っていないか
- [ ] **入力検証**: 外部入力(Gmail・API 等)すべてにバリデーションがあるか
- [ ] **依存パッケージ**: 新規追加パッケージが実在し、公式レジストリから取得しているか(ハルシネーションパッケージ確認)
- [ ] **OAuth 連携スコープ**: Gmail 等の連携スコープが最小権限になっているか
- [ ] **エラーレスポンス**: スタックトレース・内部情報がユーザーに露出しないか

### 📦 視点 5: 依存・保守視点

**目的**: 依存関係の健全性と長期保守性を確認する。

**確認項目**:
- [ ] 新規依存パッケージの追加に正当な理由があるか
- [ ] ロックファイル(package-lock.json 等)が更新・コミットされているか
- [ ] 追加パッケージに既知の脆弱性がないか(npm audit / pip audit / cargo audit 等)
- [ ] 使用していない依存が追加されていないか
- [ ] 変更が既存の他コンポーネントに破壊的影響を与えていないか
- [ ] 設定変更(環境変数追加等)がドキュメントに反映されているか

## design モード: 5 視点

設計ドキュメント(`*.md`、設計文書ディレクトリ配下の成果物等)向け。コードを直接対象としない。

### 🧭 視点 1: 要件整合性視点(段階間整合性含む)

**目的**: 上流文書と本 PR の成果物の整合性を確認する。

**確認項目**:
- [ ] PR の成果物が **上流文書**(要件 / ペルソナ / ストーリー等)の意図と一致しているか
- [ ] **段階間整合性**: 本 PR で確定した判断により、上流文書への **逆波及更新** が必要か(例: 設計段階で MVP スコープから機能を Phase 2 へ移行 → 要件文書の MVP 列挙も同期更新が必須)
- [ ] スコープクリープ(要求外の設計拡張)がないか
- [ ] AI が要件・ペルソナの意図を誤解した設計になっていないか
- [ ] 用語・命名が上流文書と一貫しているか

### 🧩 視点 2: 設計コヒーレンス視点(内部矛盾)

**目的**: 同 PR 内・同ファイル内・同セクション内の **内部矛盾** を検出する。

**確認項目**:
- [ ] 同じ事象を複数箇所で説明している場合、事実が一致しているか(例: シーケンス図と Queue 構成表の経路一致)
- [ ] 設計判断(Plan の Q&A 回答)と実装方針が一致しているか
- [ ] 章節間の参照が崩れていないか(例: 「セクション 4 参照」とあるがセクション 4 が無い)
- [ ] 表記揺れ(同一概念に異なる名前)がないか
- [ ] エラー型・データ型・API スキーマが複数箇所で食い違っていないか

### 🔍 視点 3: ハルシネーション検出視点(設計版)

**目的**: 設計ドキュメント特有のハルシネーション(存在しない参照・数値矛盾)を検出する。

**確認項目**:
- [ ] **数値整合性**: 冒頭サマリ ↔ 表合計 ↔ 各セクション本文の数値が一致するか(例: 「全 51 コンポーネント」の合計が本当に 51 か)
- [ ] **ID 参照整合性**: F-XX / U-XX / Story ID / 型名 / メソッド名が上流文書に **実在** するか(存在しない F-15 などへの参照を検出)
- [ ] **重複記述の事実一致**: 同じ事象を 2 箇所以上で説明している場合の整合性(例: 表とシーケンス図で経路が違う)
- [ ] **列挙の網羅性**: 「全 N 件」と宣言している箇所で、本文に N 件すべて存在するか(例: 「10 ユースケース」と書いて 9 個しか定義されていない場合は片手落ち)
- [ ] **メソッド・型の参照整合性**: 引数や戻り値で参照している型が他ファイルで定義されているか

#### 機械的検証手順(推奨)

ID 参照整合性 / 数値整合性は手作業だと見落としやすい。以下の grep ベース手順で機械的に検証する:

```bash
# 設計側で参照されている全 ID を抽出(F-XX / U-XX / Story ID 等、プロジェクトの ID 規則に応じて正規表現を調整)
grep -ohE "F-[0-9]+|U[0-9]+(-[A-Z0-9]+)+" path/to/design/*.md | sort -u > /tmp/design_ids.txt

# 上流文書(要件 / ストーリー)で実在する ID を抽出
grep -ohE "F-[0-9]+|U[0-9]+(-[A-Z0-9]+)+" path/to/upstream/*.md | sort -u > /tmp/upstream_ids.txt

# 設計側にのみ存在 = ハルシネーション候補
comm -23 /tmp/design_ids.txt /tmp/upstream_ids.txt

# 「全 N 件」宣言と CREATE TABLE / 行数等の実数の突合
grep -cE "^CREATE TABLE" path/to/schema.md  # 本文のテーブル数を取得して宣言値と比較
```

#### 数値整合性の機械的検証手順(推奨)

「全 N コンポーネント」「合計 N テーブル」「約 N ユースケース」のような数値表記は文書間で食い違いやすい。同一概念の数値を抽出して比較する:

```bash
# 「全 N / 合計 N / 約 N」表記をすべて列挙(対象キーワードはプロジェクトに合わせて拡張)
grep -nE "(全|合計|約|計) ?[0-9]+ ?(件|個|テーブル|コンポーネント|ユースケース|エンドポイント)" path/*.md

# 「N+M+K = Total」形式の合算式が本文に明記されているか確認(派生に転記しやすくなる)
grep -nE "[0-9]+ ?\+ ?[0-9]+.*= ?[0-9]+" path/*.md
```

抽出結果を同じ概念ごとにクラスタリングし、値のばらつきを目視確認する。レビュー時間に余裕がある場合は **「N+M+K = Total」形式の合算式を同一文書内に併記する** ことを 🟢 Suggestion として提案できる(将来の派生文書転記時の見落としを防ぐ)。

### 🔒 視点 4: セキュリティ視点(設計レベル)

**目的**: 設計ドキュメント段階で識別すべきセキュリティ要件・脅威モデルを確認する。

**確認項目**:
- [ ] 認証・認可方針が **すべての公開エンドポイント** に明示されているか
- [ ] 機密データ(トークン・PII)の保管・暗号化方針があるか
- [ ] BOLA / IDOR 防止策がリソース参照系 API で言及されているか
- [ ] 入力検証・出力エスケープの責務がどのレイヤに属するか明示されているか
- [ ] 監査ログ・改竄防止の機械的保証(トリガー・append-only 等)が指定されているか
- [ ] OAuth スコープ・最小権限原則が言及されているか
- [ ] 設計レベルの脅威モデリング(STRIDE 等)が完了基準に含まれているか

### 🏗️ 視点 5: 構築可能性視点(設計版「依存・保守視点」)

**目的**: **後続ステージ**(詳細設計 / 実装等)で本設計が **実装可能** か、未確定事項が後続を阻害しないかを確認する。

**確認項目**:
- [ ] **未確定事項のリスト化**: 後続ステージで詰まりそうな未確定パラメータ(タイムアウト・リトライ回数・Cron 頻度・コスト上限値)が **後続ステージで確定する旨** が明示されているか(単なる「TBD」放置でない)
- [ ] **拡張性ポート**: 抽象化レイヤが将来の仕様変更(別 SaaS への乗り換え等)を本当に吸収できる設計か
- [ ] **コスト・性能の達成可能性**: NFR(レイテンシ・スループット・コスト目標)達成の **設計目標値の枠組み** が示されているか(詳細値は後続でも、根拠ある上限が示されているか)
- [ ] **依存外部サービスのバージョン・SLA**: 設計時点で前提としている外部サービスの仕様が明示されているか
- [ ] **テスト戦略との接続**: モック境界・PBT 対象・E2E スコープが設計時点で示されているか

## 重要度判定基準マトリクス

### 共通レベル定義

| アイコン | レベル | 対応 |
|---------|--------|------|
| 🔴 | **Critical** | マージ前に必ず修正(ブロック) |
| 🟡 | **Warning** | 修正を強く推奨(理由があれば許容、要議論) |
| 🟢 | **Suggestion** | 改善提案(任意対応) |
| 💡 | **Note** | 情報共有・補足(対応不要) |

### 信頼度(Confidence)軸 — 必須

各指摘には重要度と **直交する信頼度** を必ず併記する。AI 含む任意のレビュアーが「断定指摘」と「仮説指摘」を区別できない問題への対処。

| アイコン | レベル | 意味 |
|---------|--------|------|
| 🎯 | **High** | 該当箇所を直接読み、外部仕様 / 標準 / 上流文書と突合済み。誤指摘の可能性は低い |
| 🤔 | **Medium** | 主要箇所は確認したが推測や前提が一部含まれる。著者側で再確認推奨 |
| ❓ | **Speculative** | 仮説段階。レビュアー側で検証不能で、PR 著者の検証要請を含む |

#### 信頼度と総合評価の対応

- **🔴 Critical / ❓ Speculative の指摘はマージブロックではなく「要検証」扱い**(著者が反証できればそのまま進めて良い)
- **🔴 Critical / 🎯 High** は通常通り `Request Changes` の根拠となる
- 総合評価のサマリーには重要度と信頼度の両方を集計する(例: `🔴 5 件(うち 🎯 4 / ❓ 1)`)

### マスター文書 vs 派生文書の判定原則

要素の **欠落 / 不整合** は、それが起きた場所がマスター文書か派生文書かで重要度を切り分ける:

| 場所 | 欠落・不整合の重要度 |
|------|---------------------|
| **マスター文書**(責務を最初に定義する文書)で欠落 | 🔴 **Critical**(ソース・オブ・トゥルースの欠陥) |
| **派生文書**(図示・要約・引用)のみで欠落 | 🟡 **Warning**(マスターには存在し、派生のみ未追従) |
| マスター ↔ 派生で **食い違い** | 🔴 **Critical**(実装で必ず齟齬) |

### 拡張(security-baseline / property-based-testing 等)連動ルール

リポジトリで Extension が **Enabled** の場合、その Extension が要求する成果物の **欠落** は **🔴 Critical に引き上げ** る。
- 例: `security-baseline` Enabled かつ STRIDE 実施結果が設計成果物に存在しない → Critical
- 例: `property-based-testing` Enabled かつ PBT 対象の特定が無い → Critical

Extension の有効状態は本リポジトリでは `aidlc-docs/aidlc-state.md` の `## Extension Configuration` で確認する。

### code モード判定例

| 種類 | 🔴 Critical | 🟡 Warning | 🟢 Suggestion |
|------|-----------|-----------|--------------|
| シークレット | API キーのハードコード | `.env.example` 未更新 | コメントの redact ガイド追記 |
| 認証・認可 | BOLA を引き起こすクエリ | 認可粒度が荒い | テスト追加 |
| インジェクション | SQL/OS コマンドへの文字列結合 | エスケープ漏れの可能性 | パラメータバインドの統一 |
| テスト | 必須経路のテスト未追加 | エッジケース未カバー | テスト命名改善 |
| 依存 | ハルシネーションパッケージ参照 | 既知脆弱性のあるバージョン | バージョン固定の方針 |

### design モード判定例

| 種類 | 🔴 Critical | 🟡 Warning | 🟢 Suggestion |
|------|-----------|-----------|--------------|
| 内部矛盾 | 同じ事象が 2 箇所で別事実(実装で必ず齟齬) | 表記揺れ・粒度不一致 | 補足が望ましい |
| ID 参照 | 存在しない Story / 型 を参照(ハルシネーション) | リンク先未生成 | 別表現が好ましい |
| 数値整合性 | サマリ数 ≠ 詳細合計 | 概算と精密値の混在 | 単位明示の不足 |
| 上流不整合 | 要件と矛盾する設計 | 要件記述が陳腐化 | 用語のゆらぎ |
| 完全性 | マスター文書で必須要素が欠落 | 派生文書(依存図・シーケンス図等)のみで欠落 | 図示があると親切 |
| セクション参照 | 「セクション N 参照」とあるが存在しない | リンク先がアンカー違い | 参照表現の統一 |
| セキュリティ | 公開エンドポイントの認証方針未記述 | 暗号化方針が部分的 | 脅威モデル参照リンク |
| 構築可能性 | 後続実装が不能な未確定事項 | 未確定事項が「TBD」のまま放置(解決時期なし) | 上限値の暫定示唆 |
| 拡張連動 | Enabled Extension の必須成果物欠落 | Extension ガイドに沿わない記述 | 関連リンク追加 |

## 出力フォーマット

レビュー出力は以下の順序で構成する:

1. **カバレッジ宣言**(出力先頭、必須)
2. **モード判定結果**(自動判定の場合は判定根拠も)
3. **PR 規模・形態の判定結果**(必要に応じて分岐内容を記載)
4. **事前確認結果**(PR テンプレート準拠)
5. **各視点のレビュー結果**
6. **総合評価**
7. **メタフィードバック節**(出力末尾、必須)

### カバレッジ宣言(出力先頭で必須)

`✅ 問題なし` の信頼性を担保するため、レビュアーが何を確認し / 何を確認しなかったかを **必ず** 明示する。

```
## 📐 カバレッジ宣言

- **総変更行数**: N 行(規模: 小 / 中 / 大 / 超大)
- **変更ファイル**: M 件
- **通読**: A 件
- **抜粋確認**(grep / セクション読み等): B 件
- **未確認**: C 件(理由ごとに列挙: 大型生成物 / バイナリ / アクセス不能 等)
- **N/A 視点項目**: 各視点のチェック項目で N/A 判定したもの一覧(該当ない場合「なし」と明記)
- **発動した規模・形態分岐**: 該当時のみ(例: 「超大規模 → 分割推奨を Warning 計上」)
```

### 単一箇所の指摘

```
### [視点名] レビュー

#### [重要度アイコン] [指摘タイトル] [信頼度アイコン]
**根拠視点**: [視点名](例: `design 視点 3 ハルシネーション検出`)
**根拠項目**: [視点内のチェック項目を引用](例: 「ID 参照整合性: F-XX / U-XX が上流文書に実在するか」)
**ファイル**: `path/to/file`
**セクション**: `## 4.2 認証`(または `### Story F-12` など、構造的参照)
**行**: L45 / L120-L135(該当する場合のみ)
**指摘**: 具体的な問題点
**提案**: 改善案または推奨アクション
```

### 複数箇所をまたがる整合性指摘

```
#### [重要度アイコン] [指摘タイトル] [信頼度アイコン]
**根拠視点**: [視点名]
**根拠項目**: [視点内のチェック項目]
**対象箇所**(複数):
- `path/to/file-a.md` セクション 3「Queue 構成」(L82, A-3 行)
- `path/to/file-a.md` シーケンス図 1(L36-49)
- `path/to/file-a.md` シーケンス図 2(L54-72)
**指摘**: 同一事象を 3 箇所で異なる事実として記述している
**提案**: 真の方針を 1 つ確定し、3 箇所を一致させる(推奨案: ...)
```

### 必須項目の意味

- **信頼度アイコン**(🎯 / 🤔 / ❓): 重要度判定基準マトリクスの「信頼度軸」参照。Critical / Speculative はマージブロックではなく要検証扱い
- **根拠視点**: その指摘がどの視点の確認項目から導かれたかを明示。レビュー全体での視点カバレッジの検算に使用
- **根拠項目**: 視点内のチェック項目をそのまま引用。同じ項目に複数指摘が立つ場合はチェック項目の分割不足のシグナル(メタフィードバック節での改善提案候補)

### 指摘がない視点(✅ 問題なし)— チェック項目全件の ✓/N/A 必須化

「指摘なし」の場合、**該当視点のチェック項目全件について `✓ / N/A(理由)` を明示** する。1 行の `✅ 問題なし` や 2〜3 点抜粋では、視点を全件確認したかが追跡できないため、過剰でも全件カバレッジを優先する。

```
### [視点名] レビュー

✅ 問題なし(チェック項目 N/N 件確認)
- ✓ [チェック項目 1 をそのまま引用]: 根拠 file:L行
- ✓ [チェック項目 2]: 根拠 file:L行
- N/A [チェック項目 3]: [N/A 理由 — 例: 本 PR は SQL 不変更のため対象外]
- ✓ [チェック項目 4]: 根拠 file:L行
...
```

例:

```
### 🔒 セキュリティ視点 レビュー

✅ 問題なし(チェック項目 8/8 件確認)
- ✓ シークレット: ハードコードされた API キー / トークンなし(`grep -nE "(AKIA|sk_|ghp_)" -r .` で 0 件)
- ✓ 認証: §4.2 認証表で全公開エンドポイントの認証方式記載: application-design.md L394-398
- ✓ 認可 (BOLA): §4.2 で user_id パラメータ権限チェック必須を明記
- N/A インジェクション: 本 PR は Markdown のみ、SQL/OS コマンド出力なし
- N/A 入力検証: 本 PR は Markdown のみ、外部入力処理なし
- N/A 依存パッケージ: 本 PR は Markdown のみ、新規依存追加なし
- ✓ OAuth スコープ: §7.4 OAuth スコープ表で最小権限を明示
- ✓ エラーレスポンス: §5.2 エラーハンドリング表でスタックトレース非露出を確認
```

## 総合評価

すべての視点のレビュー完了後、以下を出力すること:

**判定**: `✅ Approve` / `🔄 Request Changes` / `💬 Comment`

> 判定ルール:
> - `🔴 Critical / 🎯 High` または `🔴 Critical / 🤔 Medium` の指摘が 1 件でもある → `🔄 Request Changes`
> - `🔴 Critical / ❓ Speculative` のみ → `💬 Comment`(著者の検証要請、ブロックしない)
> - Critical なし → `✅ Approve`(Warning / Suggestion は判定に影響しない)

**サマリー**(重要度 × 信頼度の両方を集計):
- 🔴 Critical: X 件(うち 🎯 High Y / 🤔 Medium Z / ❓ Speculative W)
- 🟡 Warning: X 件(うち 🎯 / 🤔 / ❓ の内訳)
- 🟢 Suggestion: X 件
- 💡 Note: X 件

**優先対応項目**: (Critical / 🎯 High または 🤔 Medium のみ箇条書きで列挙、❓ Speculative は別枠で「要検証項目」として併記)

**起点 SHA**: 本レビュー時点の `HEAD` コミット SHA(短縮 7 桁可)。次回 `/review --since` 起動時の差分起点として参照される。

**レビュー反映確認用 URL**: 本レビューコメントの GitHub URL(投稿後に自分のコメントを編集して埋める運用)。`/review --since=<comment-id>` のコメント ID は URL 末尾の `#issuecomment-XXXXXXX` から取得可能。

> 補足: コメント ID は投稿前には確定しないため、URL 形式で記述すると投稿時に取得できる。コメント ID のみで運用したい場合は投稿後の編集で確定 ID を埋め込む。

## 🪞 メタフィードバック節(出力末尾で必須)

**目的**: ルール自身を実運用フィードバックで進化させるため、レビュアーが本ルール適用中に気づいた **ルール側の改善点** を構造化収集する。空でも「特になし」と明示記述する(空の宣言と未記載は別物として扱う)。

```
## 🪞 本ルールへのフィードバック

- **判断に迷った箇所**: [例: 「視点 3 と視点 2 で同一指摘が立った、振り分け基準が曖昧」/ 該当なしなら「なし」]
- **ルール文言が曖昧だった箇所**: [例: 「カバレッジ宣言の "抜粋確認" の定義が不明瞭」/ なしなら「なし」]
- **想定外のケース**: [例: 「PR が複数の独立した変更を含み、モードが揺れた」/ なしなら「なし」]
- **改善提案**: [例: 「視点 3 に "略語整合性" のチェック項目を追加してはどうか」/ なしなら「なし」]
```

このフィードバックは PR の総合評価判定には影響しない。ルールの将来改修時の主要な情報源として PR のレビュー履歴から収集される。

## 再レビュー(`--since=<comment-id>`)モード

修正反映後の差分のみを再レビューするためのモード。指摘 → 修正 → 再レビューのサイクルを効率化する。

### 起点 SHA の推定アルゴリズム

GitHub の **issue comment** には `commit_id` フィールドが無いため、以下の優先順位で起点 SHA を推定する:

1. **前回コメント本文の `起点 SHA` 表記を優先**(本ルールの総合評価フォーマットで埋め込まれている前提)
2. 表記が無い場合、**前回コメントの `created_at` 時刻** を取得し、PR コミット履歴のうち `commit.committer.date <= comment.created_at` を満たす **最新コミット** を起点 SHA とする
3. それも不能な場合、PR の **最初のコミット** を起点とする(全件再レビュー、警告ログ出力)

### 手順

1. 引数 `--since=<comment-id>` から **起点となる前回レビューコメント** を取得
   - GitHub MCP の `pull_request_read` で `get_comments` / `get_review_comments` から該当コメントを取得
2. 上記アルゴリズムで **起点 SHA** を推定し、`<起点 SHA>..HEAD` の **差分 commit 一覧** を取得
3. 前回コメントの **全指摘(Critical / Warning / Suggestion / Note)を一覧化**
4. 各指摘について **解決状況を判定**:
   - ✅ 解決(該当箇所が修正されている)
   - ⚠️ 部分解決(一部のみ修正)
   - ❌ 未解決(変化なし)
   - ❓ 確認不能(該当箇所が大幅に変わって直接比較できない)
5. **新規検出された問題** がある場合、以下の 3 分類で出自を必ず明示:
   - 🆕 **New**: 本区間(起点 SHA..HEAD)のコミットで **導入された** 問題
   - 🙇 **Missed**: 起点 SHA 時点で **既に存在していた**、前回見落とし(レビュアーの自己申告)
   - 🔄 **Resurfaced**: 一度修正されたが本区間で **再発** した(リバート / 再導入の可能性)

   この分類はレビュアー(人間/AI 問わず)の品質指標として独立価値を持つ。AI レビュアーの場合、`🙇 Missed` は前回プロンプト時の見落とし率として観測される。
6. 総合評価では「前回 Critical N 件 → 今回 0 件」のような **解決ステータスサマリ** に加え、新規検出の分類別件数(🆕 X / 🙇 Y / 🔄 Z)も提示

### 出力フォーマット(再レビュー版)

```
## 📐 カバレッジ宣言
[初回と同様: 確認対象、未確認、N/A 視点項目を明示]

### 🟢 修正確認

**起点 SHA**: <推定された SHA>(推定根拠: 前回コメント本文 / created_at 時刻 / その他)
**差分コミット**: <起点 SHA>..<HEAD SHA>(N コミット)

#### 前回指摘の解決状況

##### 🔴 Critical(N 件 / 全解決)

| ID | 検証結果 |
|----|---------|
| **C1** [前回指摘の要約] | ✅ 完全解決。[根拠ファイル/セクション]で確認 |
| ... | ... |

##### 🟡 Warning(M 件 / X 件解決 / Y 件部分解決 / Z 件未解決)
...

#### 新規検出(🆕 New / 🙇 Missed / 🔄 Resurfaced)

各指摘には初回レビューと同じ必須項目(信頼度 / 根拠視点 / 根拠項目)を付与する:

```

**根拠項目**: 「コメント: 「何を」でなく「なぜ」を説明するコメントが書かれているか」


## 補足: モードに応じた省略ルール

- **code モード で動作確認の Critical** が PR 属性に `changes-aidlc-stage` を含む場合は緩和(代わりに「上流成果物との整合性確認」を必須化)
- **design モード で QA / 依存・保守視点** は適用せず、代わりに **設計コヒーレンス / ハルシネーション / 構築可能性視点** を実施
- **ハイブリッドモード** では code 5 視点 + design 5 視点 = **全 10 視点を独立に実施**(視点間で観点が重複しても統合せず、相互検証として両方記載する)
- **`--since` 指定時** は事前確認をスキップ可(初回レビューで実施済の前提)。ただし **カバレッジ宣言 / メタフィードバック節は省略不可**
